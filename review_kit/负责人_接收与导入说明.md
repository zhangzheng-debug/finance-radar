# 负责人接收与导入说明

## 交付方式

分别把 `成员A/` 和 `成员B/` 文件夹压缩后交给两个人。两人不得交换答案，也不要在双方完成前把原始审核结果提交到公开 GitHub。

组员只需交回各自唯一的 `.review.json` 文件。不要让组员安装项目、接触 AWS、生产数据库、Reviewer token 或 `.env`。

`批次摘要.json` 会记录来源账本哈希、事件总数和最后更新时间。本工具只认冻结的事件版本与证据指纹；若首包来自本地历史快照，它适合校准流程，但不能冒充截图中当前生产队列的完整导出。正式扩大批次前，应在服务器上对生产账本执行一次只读 `build`，然后再把新包发给组员。

## 验收与合并

```powershell
python scripts/event_fact_review_kit.py validate `
  --assignment "负责人材料\assignment_A.json" `
  --submission "成员A交回.review.json"

python scripts/event_fact_review_kit.py validate `
  --assignment "负责人材料\assignment_B.json" `
  --submission "成员B交回.review.json"

python scripts/event_fact_review_kit.py merge `
  --assignment-a "负责人材料\assignment_A.json" `
  --submission-a "成员A交回.review.json" `
  --assignment-b "负责人材料\assignment_B.json" `
  --submission-b "成员B交回.review.json" `
  --output "consensus.json" `
  --authorization-template "authorization.template.json"
```

合并只生成共识和冲突报告，不修改数据库。事件版本或证据变化会在正式应用时被 CAS 拦截为 `STALE_REVIEW`。

两人的结果可先通过微信、U 盘或私密文件传输交回。若以后走 GitHub，两人必须都完成后再同时上传；不要让第二个人在审核期间看到第一人的公开 PR。

## 正式应用边界

`authorization.template.json` 默认 `approved=false`。只有所有者检查汇总数量、冲突和目标状态后，才能填写动作级授权。正式应用命令强制先创建并验证 SQLite 备份，且任一事件版本/证据指纹变化都会让整个批次失败关闭。

不要把“结果文件格式有效”理解成“已经部署”或“可以自动改生产”。审核记录进入 GitHub、生成正式化计划、正式应用和生产部署是不同动作。
