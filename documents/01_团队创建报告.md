## 3. 产品目标与范围

金融雷达把多源公开材料处理为可审计的事件链：

```text
来源材料 → 原始观察 → 规范事件 → 事件版本
                              ├─ 证据关系
                              ├─ 千问风险语义
                              ├─ DeepSeek 阅读辅助
                              └─ 资产映射与市场观察
```

当前产品范围包括：

- 监管、宏观、发行人和公开新闻线索的持续采集；
- 事件归并、原子化、版本化与来源修订；
- “材料可读”与“事实可正式引用”分层；
- 千问对极性、重大性、负面强度和研究优先级的结构化研判；
- DeepSeek 对特定无证据捕获文本的后台阅读辅助；
- 公司证券、国家 ETF、BTC/IBIT、黄金、原油、利率等资产映射；
- 消息发布后价格窗口、搜索筛选、稳定深链和公共只读 GET API；
- AWS 上的服务隔离、备份验证、发布回滚和运行验收。

产品不提供下单、仓位、余额、交易执行或投资建议。模型结果、来源事实和价格观察彼此隔离，价格只作为发布后的研究上下文。

## 4. 团队工作方式

### 4.1 Scrum 约定

- PO 维护产品愿景、待办优先级与验收边界；
- SM 组织迭代、排除阻塞并维护会议与复盘记录；
- QA 依据可复现的验收标准执行测试，不以口头描述代替证据；
- 每个 Sprint 均包含 Goal、Backlog、Review、Retrospective 和下一轮结转；
- 需求冲突时优先保护“事件—原文—研判—市场反应”的核心闭环。

### 4.2 Git 与评审约定

- GitHub 为正式协作与发布主源，Gitee 用于同步和现场备用；
- 功能在独立分支完成，经 diff、测试和 PR 审核后进入发布线；
- 不在脏工作区覆盖队友修改，不把本地测试通过等同于生产部署；
- 生产变更必须保留精确提交、发布清单、验收结果和回滚路径；
- 密钥、令牌、个人凭据不得写入仓库、课件、截图或日志。

### 4.3 Definition of Done

一项任务只有同时满足以下条件才记为“完成”：

1. 功能与产品范围一致，未引入交易写能力；
2. 输入、空值、超长文本、网络失败和权限边界有明确处理；
3. 定向测试和全量质量门通过；
4. 页面、API 或 Worker 的结果可用真实数据复核；
5. 相关文档、配置样例和回滚说明同步更新；
6. 若涉及生产，loopback 与公网均验收，并形成发布收据。

## 5. AI 协作声明

本项目不设置预先禁止 AI 参与的代码、测试、文档或运维区域。AI 可参与需求拆解、架构比较、代码实现、测试生成、故障诊断、文档整理和发布检查。团队不把 AI 的自述当成验收证据，而使用以下质量门承担最终责任：

- 事实准入由确定性证据合同控制；
- 模型由冻结数据、哈希、枚举合同和版本绑定控制；
- 代码由 Git diff、单测、CI、秘密扫描和 no-trading 扫描控制；
- 生产由发布清单、备份恢复、Nginx 检查和公网验收控制；
- 云资源、密钥与最终发布由负责人明确授权；
- 展示、现场操作和临时修改由学生本人完成并负责。

## 6. 决策与争议处理

1. 事实、模型和行情发生冲突时，以原始来源和证据合同为事实依据；
2. 新 UI 破坏数据、模型、滚动或深链时，回到稳定正式版，再以最小增量集成；
3. 评测口径发生冲突时，优先采用可复算的冻结集和完整指标，不挑选最高数字；
4. 生产变更失败时先回滚，不在故障现场继续叠加未经验证的修改；
5. 个人贡献争议以提交、PR、文档、测试记录和本人签字为准。
