# Finance Radar 产品章程

状态：当前产品决策基线
生效日期：2026-08-13

## 1. 产品定义

Finance Radar 是面向个人研究者的只读金融事件证据雷达。它持续发现多源事件、压缩重复报道、保存原始证据与修订时间线，并帮助人快速判断“发生了什么、证据是否足够、还缺什么”。系统在证据不足或冲突时必须保留不确定性；AI 只辅助筛选和解释，最终判断由人完成。

## 2. 用户优先级

所有需求按以下顺序决策；低优先级工作不得损害更高优先级体验。

1. **个人研究者**：快速发现事件、筛选关注范围、核对原始证据、理解时间线和保存个人工作视图。
2. **公共展示访问者**：通过只读界面理解事件、证据、系统新鲜度和方法边界。
3. **课程、开发与运维参与者**：复核、模型治理、故障诊断、备份恢复、演示和课程过程证明。

判断新功能是否进入主产品时，必须先回答：它是否缩短个人研究者从发现事件到核对证据的路径？若答案是否定的，应放入内部工具、报告或演示材料，而非公共首页。

## 3. 核心产品闭环

```text
多源发现
  -> 去重、规范化和版本记录
  -> 原文证据、冲突与缺口检查
  -> 只读行情作为事后上下文
  -> Web 事件流、证据与下一步行动
  -> 人工判断
  -> 可审计回放与修订
```

当前采用 **Web-first**：Web 是唯一主要事实与工作界面。Telegram 是可选提醒和深链通道，默认未启用；除非操作者另行明确授权并通过审计化启用流程，否则文档和界面不得把它描述为正在发送的生产能力。

## 4. 不变边界

- 不下单、撤单或调整仓位，不读取账户、余额或资金信息。
- 不生成投资建议、仓位建议或收益承诺。
- 行情只用于事件上下文和事后观察，不用于反向证明消息真伪。
- AI 和影子模型不得自动确认事实、改写正式结论或绕过证据、冲突及晋级门。
- 聚合标题、社交内容和 Telegram 线索不得单独成为最终事实依据。
- 原始证据、修订、失败、冲突、弃权和人工分歧不得被隐藏或改写成成功。
- 不绕过登录、付费墙、网站条款、访问限制或反爬措施。
- 密钥、令牌、账户信息和恢复口令不得进入源码、数据库、报告、日志或公共界面。
- 实时数据、历史快照和演示数据必须明确区分；不得用缓存或演示内容冒充当前结果。

## 5. 已接受的目标变更

最初的零增量现金成本目标已被后续明确批准的 AWS 生产部署取代。当前接受为该产品承担一台受资源约束的 AWS 主机及必要存储成本，但这不是无上限授权。

成本原则：

- 先优化现有资源、停用无用服务，再考虑扩容。
- 新增长期计费资源必须说明用户价值、月度理论成本、停止方式和数据保全方式。
- 课程演示、模型实验和冗余计算不得默认扩大长期账单。
- 账单、实例规格和在线状态属于易变事实，发布前必须现场核验，不能只引用历史报告。

## 6. 产品 KPI

产品 KPI 与工程健康、课程评分分开报告。每个指标必须同时给出测量窗口、样本量、数据来源和“未测量/不可用”状态。

| 维度 | 核心指标 | 解释 |
|---|---|---|
| 发现 | P0/P1 来源捕获延迟 P50/P95 | 从来源可获取到本地首次记录 |
| 去重 | 重复压缩率、错误合并率 | 减少重复阅读，同时避免合并不同事件 |
| 覆盖 | 注册来源成功率、来源新鲜度、硬事件召回抽样 | 不以来源数量代替有效覆盖 |
| 证据 | 可引用原文覆盖率、证据闭合率、冲突/证据不足率 | 衡量事件是否真正可核验 |
| 效率 | 发现到打开原文的点击数和用时、待复核队列年龄 | 衡量个人研究者的实际工作成本 |
| 质量 | 正式结论抽样准确率、撤回/更正响应时间 | 人工抽样，不用模型自评代替 |
| 提醒 | 符合条件的通知覆盖率、重复率、延迟 | 仅在 Telegram 被明确启用时报告；否则标记“未启用” |
| 信任 | 过期数据误标实时次数、边界违规数 | 目标均为 0 |

测试通过数、备份恢复、服务可用性和模型门禁仍是必要工程指标，但不得替代上述用户价值指标。

## 7. 界面与权限路线图

### Public reader

- 只读事件流、中文事实摘要、状态、新鲜度、证据节选、原始来源和方法边界。
- 支持筛选、搜索、排序、分页和本机保存的个人视图。
- 不显示内部 ID、原始 JSON、流水线 trace、服务控制、模型运行时或写入动作。

### Reviewer / operator

- 专注待复核队列、完整原文、证据矩阵、修订、冲突、只读行情和人工判断。
- 可进行有身份、有理由、不可变留痕的受控复核写入。
- 默认不展示部署、备份、模型调试和原始运行诊断；必要时通过渐进披露访问。

### Developer / admin

- 访问来源游标、任务、trace、模型卡、故障、备份恢复、发布和服务状态。
- 执行模型运行、模式切换或维护动作时继续使用显式确认、最小权限与审计记录。
- 仅回环监听并通过受控隧道按需开启，不设置公网管理路由。

实施顺序：先完成角色信息架构和只读/写入合同，再考虑新增账户系统或前端框架。角色分层不得削弱现有公网与内部网络隔离。

## 8. 产品变更门

每个新需求至少记录：目标用户、要解决的任务、成功指标、数据与权限影响、月度成本影响、失败/回滚方式。以下任一情况默认拒绝进入公共主界面：

- 只服务答辩或内部证明；
- 主要展示数据库、模型或服务实现细节；
- 没有可测用户结果；
- 需要弱化只读、证据或不确定性边界；
- 与现有功能重复但增加导航和认知负担。

## 9. 文档事实层级

1. 本章程：稳定的产品目标和边界。
2. 当前状态清单：版本、生产发布、服务、测试、备份和成本等易变事实。
3. 发布说明和验收报告：特定时间的证据快照。
4. 历史计划、课程材料和旧迁移报告：历史背景，不代表当前状态。

任何易变事实都必须现场核验；历史快照不得被重新表述为当前运行结论。
