# Finance Radar 下一阶段计划

日期：2026-08-15

依据：Claude 审计复核、目标一致性审计、`2026.08.15.4` 生产验收

## 目标

下一阶段只回答一个问题：Finance Radar 是否真的让个人研究者更快完成“发现事件 →
阅读原始证据 → 识别不确定性 → 决定是否继续跟进”的闭环。

工程健康、课程材料、模型实验和恢复证据仍需维护，但不得再替代产品价值。模型保持
shadow/advisory-only，系统保持只读，不新增交易、账户余额、仓位或自动事实确认能力。

## 阶段 1：先修首次使用体验（P1）

建议周期：1 个短迭代。

工作范围：

1. 对首页昂贵聚合做查询剖析，把事件计数、产品 KPI、来源状态和备份状态拆开测量。
2. 将可稳定复用的统计改为带生成时间的有界缓存；事件列表优先加载，运维指标延后。
3. 为加载中、来源降级、缓存时间和超时增加用户能理解的中文状态，不展示后台异常栈。
4. `/health` 分成便宜的进程活性合同和较慢的详细诊断合同，部署门只依赖有界活性检查。

验收门：

- 公网冷启动 3 秒内出现可操作框架和明确状态；10 秒内出现首屏事件流。
- 首页不因备份全量扫描、产品 KPI 聚合或单一来源超时而整体空白。
- 公开页面控制台无错误；API/Web/Worker cgroup 无 OOM，Worker 周期不被 UI 查询拖慢。
- 真实浏览器至少做桌面、窄屏、首次会话和缓存命中四组计时并保留证据。

## 阶段 2：证明结论质量，而不是证明系统复杂（P1）

建议周期：连续 2–4 周滚动抽样。

工作范围：

1. 从待核验事件按来源层级、事件类别、证据状态和时间分层抽样，避免只挑容易案例。
2. 使用 Reviewer 工作面记录证据是否足够、正式结论是否改变、是否撤回以及理由。
3. 对同一小样本做独立复核，记录一致率和分歧类型；AI 输出不得进入盲审输入。
4. 形成最小质量看板：到达原文用时、可引用证据覆盖、结论变更率、撤回率、队列年龄。

验收门：

- 至少覆盖 3 个来源层级和 5 个主要事件类别，而不是只报告总体平均数。
- 每个质量数字都能回到抽样定义、事件 ID、证据 ID、复核者和冻结时间。
- 样本不足时显示 `UNAVAILABLE` 或置信区间，不用模型自评替代人工质量证据。
- 若复核经常改变正式结论，优先修证据与规则，不扩大模型权限。

## 阶段 3：收紧个人研究闭环（P2）

触发条件：阶段 1 达标，阶段 2 已获得第一批可信数据。

只从以下能力中按实际复核数据选择一到两个：

- 关注主体/主题与浏览器本机保存筛选；
- 同一事件的修订时间线和“自上次查看后的变化”；
- 证据补齐、正式更正或来源冲突的只读提醒；
- 从事件卡片一跳到精确原文段落，并能返回原筛选位置。

验收门：

- 用实际任务测量“找到值得看的事件”和“到达原始证据”的时间是否下降。
- 不为了个性化先建账户系统；能在浏览器本机完成的状态不上传服务器。
- 不恢复默认 Telegram 外发；若未来启用，必须单独授权并保持幂等、可撤回、无交易建议。

## 阶段 4：运维诚实性与仓库降噪（P2/P3）

可与阶段 2 并行，但不得抢占产品性能与真实复核资源。

工作范围：

1. 由特权备份流程原子生成最小状态收据，绑定 snapshot、manifest hash 和验证时间；
   公开 API 仍不得获得备份目录读取权。
2. 将“服务活着、Worker 最近成功、某来源降级、备份已验证但低权限不可探测”分开表达。
3. 后续仓库只保留代表性渲染和小型证据；完整批次放 GitHub Release，不重写历史。
4. 校验 C 盘已忽略的大型迁移/数据资料后迁往 D 盘；没有校验和不得删除原件。
5. 每日备份继续保持一份；任何异机多版本恢复点都需要单独成本与权限决定。

验收门：

- 公共状态不再把 `UNVERIFIABLE_PROTECTED` 误解为失败，也不把旧数据库记录误报为新鲜实体。
- Git 新增报告资产有明确保留理由，CI 继续通过秘密、交易写路由、换行和 Shell 门禁。
- 所有迁移记录分别写明 copied、validated、cut over 和 source cleanup，不用“已复制”冒充完成。

## 明确不做

- 不接券商、交易所账户或订单接口；不读取余额、仓位；不输出仓位建议。
- 不让模型自动升级事件为 `VERIFIED`，不把启发式分数包装成概率。
- 不因 AWS 积分存在就增加实例、GPU、数据库或常驻本地 LLM。
- 不把课程答辩页、trace、原始 JSON 或运行按钮重新塞回 Public UI。
- 不在缺少真实用户/复核证据时继续扩大来源数量和模型种类。

## 决策节奏

每个阶段结束只做一次 go/no-go：提交测量证据、失败案例、成本变化和下一阶段最小范围。
如果性能或人工结论质量没有改善，就回到根因修复；不能以“又完成了很多功能”作为通过。
