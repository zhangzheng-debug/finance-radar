# Finance Radar 所有者意图与系统细则

状态：`ACTIVE / CANONICAL`

版本：`2026.08.17.1`

适用对象：产品、研究、数据、模型、前端、后台、运维、发布，以及参与本项目的人员和 AI Agent

## 0. 为什么存在这份细则

这份文件把项目从 V2 至今反复确认、但容易被聊天、旧项目书、课程材料和临时运维任务掩盖的所有者意图固化下来。它不是一次发布状态报告，也不宣称某台服务器此刻在线；它回答的是：**这个系统为什么存在、什么永远不能做、什么必须怎样做、发生冲突时听谁的。**

机器可读的治理审计清单位于 [`config/owner_intent_policy_v1.json`](../config/owner_intent_policy_v1.json)；完整测试会核对关键枚举、授权字段、运行时常量和强制规则 ID。它不是运行时模型或事实判断的数据源。正文是语义权威，机器文件是仓库级防漂移门，二者必须同一提交更新。

关键词按下列含义使用：

- **必须 / 禁止（MUST / MUST NOT）**：不可协商边界。违反即停止发布或回滚。
- **应当（SHOULD）**：默认做法；偏离时必须记录理由、影响和恢复方式。
- **可以（MAY）**：受前述边界约束的可选实现。
- **`P` 永久原则**：只有所有者后续明确改变方向并留下决策记录才能修改。
- **`C` 易变事实**：必须带核验时间和证据；不得从旧报告推断当前状态。
- **`H` 历史背景**：用于解释演化，不得重新覆盖现行规则。
- **`SUPERSEDED` 已取代决定**：保留其历史理由，但禁止无意复活。

## 2. 从头到尾的意图演化

### 2.1 V2：个人、多资产、低成本的事实雷达

最早可靠基线是 2026-07-16 的 V2 项目书：服务个人研究者，覆盖方向包括美股、ETF、宏观、商品、外汇和主要加密资产；持续发现、去重、核对官方证据、保存时间线、观察事件后行情，并通过事件线程帮助人复盘。最初要求零增量付费 API、严格只读、不得交易。

V2 曾在逐资产影响 schema 中允许 `LONG / SHORT / NEUTRAL / ABSTAIN` 研究字段；风险路由模型从来不以此为任务。这个字段虽不是券商操作，却容易被误解为交易方向，现行生产管线因此只允许 `ABSTAIN`。

### 2.2 V4–V6：Web、下行风险路由与课程工程化

Web Situation Room 取代 Telegram 成为主界面；系统明确为“全极性事实核验 + 重大下行风险优先级 + 可审计回放”。历史下行语料被澄清为风险复核语料，不是 LONG/SHORT 数据；严重度也不是价格方向。课程答辩、模型治理、部署恢复和演示证明后来占据了较多工程篇幅，但不应压过个人研究者。

### 2.3 当前：重新以个人研究闭环为中心

当前优先级固定为：个人研究者第一、公共展示第二、课程/开发/运维第三。公共前端只保留用户或演示观众真正需要理解的事件、证据、新鲜度和方法边界；内部证明、trace、模型运行和服务控制回到后台或报告。

## 3. 产品使命与范围

- `FR-PROD-001 · P`：Finance Radar 是**面向个人研究者的只读金融事件证据雷达**，不是交易终端、新闻门户或自动事实裁判。
- `FR-PROD-002 · P`：北极星是缩短“发现值得看的事件 → 打开原始证据 → 识别冲突和缺口 → 决定是否继续研究”的时间，同时帮助人在证据不足时停止下结论。
- `FR-PROD-003 · P`：核心闭环必须保留多源发现、规范化、去重、不可变观察、修订与事件版本、精确证据、冲突/缺口、只读行情上下文、人工判断和可审计回放。
- `FR-PROD-004 · P`：用户优先级固定为个人研究者、公共展示访问者、课程/开发/运维参与者；低优先级需求不得损害高优先级体验。
- `FR-PROD-005 · P`：多资产是长期覆盖方向，不是对当前实时覆盖的虚假声明。每类资产和来源必须如实报告已实现、降级、未启用或未测量。
- `FR-PROD-006 · P`：不以来源数量、页面数量、模型数量、测试数量或答辩材料数量代替用户价值。
- `FR-PROD-007 · P`：不建设机构级超低延迟终端、不做全网全文复制、不依赖单一聚合器，也不为“显得高级”引入微服务、GPU 或基础设施堆叠。

## 4. “做空特化”的唯一有效定义

> Finance Radar 面向做空研究场景，特化于发现和复核可能造成普通股、合法性、流动性或经营持续性重大受损的事件。但现阶段模型任务只是：判断一个有证据约束的事件是否值得优先交给人做下行风险复核。

- `FR-SHORT-001 · P`：**产品账本与事实核验保持全极性；偏空特化只存在于重大不利事件的风险复核路由层。**
- `FR-SHORT-002 · P`：正面、中性、普通管理事务、有偿并购退市、机械反拆、陈旧/重复和误报必须保留，作为完整事实账本和非目标控制。
- `FR-SHORT-003 · P`：风险路由器唯一允许的决策是 `RISK_REVIEW`、`NON_TARGET`、`ABSTAIN`。
- `FR-SHORT-004 · P`：模型禁止输出或衍生 `LONG`、`SHORT`、价格方向、目标价、预期收益/跌幅、时机、期限、仓位、杠杆、止盈止损、提醒许可和订单许可。
- `FR-SHORT-005 · P`：下行事件优先源自尾部风险、突发性和核验时效，不代表“负面新闻一定跌得更多”。
- `FR-SHORT-006 · P`：`event_asset_impacts.direction` 是遗留 schema，现行生产合同必须保持 `ABSTAIN` 且 `no_trading=1`。任何恢复方向研究的提案都必须使用独立迁移和独立项目边界，不能进入现有风险模型、通知或操作入口。
- `FR-SHORT-007 · P`：把本系统接入券商、生成可执行做空信号或管理仓位属于另一个项目；需要新的、动作明确的授权和独立安全审查。

## 5. 事件本体、身份、时间和严重度

### 5.1 事件身份与因果链

- `FR-EVT-001 · P`：事件必须绑定事件发生时可验证的发行人/法律实体和稳定证券标识；不得用当前 ticker、后来别名或 Q/F/Y 后缀回填历史。
- `FR-EVT-002 · P`：同一因果链必须区分 `primary / support / followup / consequence / admin`，避免把破产与其退市后果重复计为两个独立硬标签。
- `FR-EVT-003 · P`：申请、签署、定价、法院确认、计划生效、资产出售、退市程序、旧股注销和最终分配必须记录为不同节点、日期和版本。
- `FR-EVT-004 · P`：来源发布时间、聚合观察、本地接收、落库、处理、核验、通知和行情观察时间必须分开；首次抓取不得冒充官方发布时间。
- `FR-EVT-005 · P`：未来法律结果、未来融资、后来身份、旧标签和模型输出不得回填到事件当时的判断。
- `FR-EVT-006 · P`：未决法律事件可以使用发现窗口和最长 180 天结局跟踪窗口；结局窗口只解决终局，不得用于发现排序或行情回看。

### 5.2 S / A++ / A / B / C 的精确定义

这些等级表达事实终局性、可逆性和研究优先级，不表达价格方向、跌幅或交易确信度。

| 等级 | 有效含义 | 不能据此推断 |
|---|---|---|
| `S` | 核心合法性/真实性死亡，或普通股已被制度性牺牲；必须有原始且已生效的终局证据 | 必跌、归零时点、可做空 |
| `A++` | 公司自身难以修复，但外部救助仍可能改变普通股结局 | 旧股已终局、必然零回收 |
| `A` | 严重，但仍可能通过融资、经营、资产处置或管理变化解决 | 必然退市或破产 |
| `B` | 普通经营或情绪利空、可逆结构事件 | 重大尾部风险 |
| `C` | 噪音、传闻或仅有价格异常 | 已发生真实基本面事件 |

- `FR-GRADE-001 · P`：Chapter 7、Chapter 11、重组支持协议、计划确认、计划生效和旧股命运不得混写；只有终局安排已生效且旧普通股确实注销、无分配或零回收时，才可建立独立 `S` 事件。
- `FR-GRADE-002 · P`：反向拆股本身通常是结构/合规事件，绝不自动等于看空或 `A`；实际发行、权证、可转债、控制权迁移或融资压顶须另有精确证据并形成独立事件。
- `FR-GRADE-003 · P`：退市必须区分有偿并购、私有化、自愿退出、ADR/ADS 退出、另有主要市场、上市不合规、破产后果和监管强制；Form 25 只证明程序。
- `FR-GRADE-004 · P`：负净资产、低股价、单季利息覆盖、迟交文件、持续经营关键词或供应商标签不得机械升级；必须读现金、现金流、债务、契约、runway、融资依赖、资本结构、行业和否定语境。
- `FR-GRADE-005 · P`：价格暴跌只能触发向前寻找原始因果文件，不得反过来生成事实、严重度或目标标签。

## 6. 来源、证据和正式结论

### 6.1 来源与极性必须正交

- `FR-SRC-001 · P`：P0/P1/P2/P3 表达来源与证据权威；正面/中性/负面表达事件极性；二者不得共享字段、颜色或推理捷径。
- `FR-SRC-002 · P`：P0 只能支持原文明确陈述的事实，不自动提供风险等级、法律含义、股权结局或目标标签。
- `FR-SRC-003 · P`：聚合标题、OpenNews 分数、社交媒体、X、Telegram、供应商元数据和价格异常只可用于发现或上下文，不能单独确认重大事实。
- `FR-SRC-004 · P`：转载必须追溯原始出处并记录 `independence_group`；同一原文的多次转载不得冒充独立确认。
- `FR-SRC-005 · P`：不得绕过登录、付费墙、robots、条款、访问控制或反爬限制。受限内容只记录可合法保存的元数据和政策跳过原因。

### 6.2 证据生命周期

- `FR-EVD-001 · P`：正式结论必须可回到可寻址来源、原文/允许保存的快照、精确 passage、发布时间、抓取时间、内容哈希、事件版本和修订关系。
- `FR-EVD-002 · P`：发现 accession、URL 或候选文件不等于找到支持。没有精确匹配时必须保留 `PENDING_EVIDENCE_REVIEW` 或不足状态，不得写成终局失败或成功。
- `FR-EVD-003 · P`：Evidence Agent 只有在关键 claim 获精确支持且无未解决冲突时才可给出 advisory `EVIDENCE_READY`；不足时为 `INSUFFICIENT`，冲突时为 `HUMAN_REVIEW`。这些不是 canonical event status。
- `FR-EVD-004 · P`：证据回执必须绑定事件版本和证据指纹；证据或版本变化后，旧 Agent 决策和 override 必须失效并重新核验。
- `FR-EVD-005 · P`：passage 与 claim 至少要通过实体、事件关系和语义关联门；仅“token overlap 最大”且最大值为零不得算支持。
- `FR-EVD-006 · P`：原始观察不可变；来源修订和事件版本只追加。不得静默覆盖、隐藏撤回、冲突、失败或人工分歧。
- `FR-EVD-007 · P`：Sharadar 等供应商表和启发式探测只能创建 `candidate`；只有独立证据流程可产生 `verified / weak / rejected`。
- `FR-EVD-008 · P`：canonical event status、人工裁决的 `evidence_state` 轴、Evidence Agent status 和 risk-router evidence gate 是四个独立命名空间。risk-router 的 gate 不是 `PRIMARY_SUPPORTED_*` 时必须直接 `ABSTAIN`，且不得调用语义模型或显示置信度；任何命名空间都不能自动写另一个命名空间。

## 7. 粗审、轻量细核与正式人审

三者必须分开命名、授权、写入和报告。

### 7.1 粗审

- `FR-REV-001 · P`：粗审是机器或人工的队列分诊，可以记录相关性、弱证据、冲突和继续研究建议；不得改变 canonical label/status，不得成为训练真值。
- `FR-REV-002 · P`：批量粗审必须明确 `formal_verification=false` 和机器/人工模式；不能把“处理了四千条”写成“正式核验了四千条”。

### 7.2 相对细核（轻量细核）

- `FR-REV-003 · P`：轻量细核的目标是用有限成本产生**足以改变正式结论或模型看法**的有用输出，不做逐字逐句的无限审阅，也不允许空泛概括。
- `FR-REV-004 · P`：每条轻量细核至少检查：事件时实体/证券身份、事件链节点与日期、P0/P1 精确 passage、materiality、polarity、evidence state、关键反证/冲突、理由和未解决问题。
- `FR-REV-005 · P`：可以按事件家族批量预处理和模板化字段，但正式化只能在支持的事件家族内，由有到期时间、精确事件清单、事件版本、证据指纹、操作者和目的的显式授权批次执行。
- `FR-REV-006 · P`：常驻 Worker 永远不得携带 evergreen light-verify 权限；后台自动循环使用 `--no-light-verify`。

### 7.3 正式训练标签与质量声明

- `FR-REV-007 · P`：可用于正式训练/评估的真标签必须由两名真实不同审核者互盲独立判断；不一致由第三名独立仲裁。
- `FR-REV-008 · P`：盲审隐藏来源身份（在可行范围内）、目标标签、旧标签、模型/同伴答案和事后市场结果；人只提交精确 passage、重大性、极性、证据状态和理由，目标标签最后由纯函数派生。
- `FR-REV-009 · P`：AI 不得批量冒充真实人审、复制理由、伪造双审、教师批准或学生工作。
- `FR-REV-010 · P`：当真实双审未完成时，必须写 `NOT_READY`；不得以 AI rubric、高测试数或 shadow 指标替代人类标签来源。
- `FR-REV-011 · P`：真实审核身份和角色必须由服务端把独立凭据绑定到不可变主体；客户端不得自报或切换 `reviewer_id/role`，共享 Reviewer/Admin 令牌不得冒充两名审核者或第三仲裁者。
- `FR-REV-012 · P`：真人盲集只允许使用事件时点已存在的内容；冻结前必须完成真实 issuer/event-chain 分组、精确与近重复清零、至少一个完整来源家族留出、数据集与样本 ID 集哈希和一次性不可逆冻结。冻结授权必须是独立文件并精确绑定动作、到期时间、freeze ID、两类哈希、数量与来源留出；命令行自报身份不构成授权。样本状态和完整冻结收据必须同一数据库事务提交，只允许完全相同的幂等故障恢复。旧合同样本可以保留审计，但不得进入新队列或阻挡诚实的 `NOT_READY`。

## 8. Evidence Agent 与风险路由模型

- `FR-AI-001 · P`：Evidence Agent 与风险路由器是两个职责。前者提出受约束的 claim/证据关系/中性摘要，后者只做下行风险复核排队。
- `FR-AI-002 · P`：Evidence Agent 是 advisory-only；结构化证据图和确定性规则只决定 eligibility。只有明确授权的 canonical mutation path 或真实人审能改变正式状态，Evidence Agent 即使给出 deterministic `EVIDENCE_READY` 也没有写权。
- `FR-AI-003 · P`：本地小语言模型默认禁用、仅回环、限资源；非法 JSON、未知 claim/citation、伪造引用、提示注入、越界或结论不一致使整次输出无效并回退确定性结果。
- `FR-MDL-001 · P`：结构化证据门先于语义模型；非 `PRIMARY_SUPPORTED_*` 输入必须由 `DETERMINISTIC_EVIDENCE_GATE` 直接返回 `ABSTAIN`，`semantic_model_invoked=false`、`confidence_applicable=false`，UI 不显示置信度。
- `FR-MDL-002 · P`：每次运行保存实际是否调用语义模型、`decision_source`、`confidence_applicable`、输入/证据/配置/模型哈希；UI 只有在 `confidence_applicable=true` 时显示置信度。
- `FR-MDL-003 · P`：训练特征禁止事件正式状态、人工等级、内部 taxonomy、来源捷径、旧模型输出、事件后价格/收益、账户、仓位和订单信息。
- `FR-MDL-004 · P`：数据切分必须同时按时间、issuer 和 event-chain 分组，并执行 source-family holdout、精确/近重复清零；“近重复”必须使用真实相似度判定，不能以规范化文本等值哈希冒充。盲集在推理前冻结并哈希，暴露后永不再用于调参。
- `FR-MDL-005 · P`：晋级不能只看 accuracy；必须同时报告 macro-F1、`RISK_REVIEW` recall、`NON_TARGET` false-risk、`ABSTAIN`、泄漏/重叠、来源留出和标签 provenance。
- `FR-MDL-006 · P`：失败的 legacy external-blind-v1 和 legacy external-blind-v2 工件永久保留；后续 v4 AI-rubric blind-v3 指标改善不能抹除历史失败，也不能冒充尚未冻结的 V3 authentic-human blind-v2。
- `FR-MDL-007 · P`：`QUALIFIED_SHADOW` 只允许继续咨询式队列路由；不等于事实核验、正式判断器、告警许可或交易晋级。任何非 shadow 激活都必须先有真实双盲标签、全部晋级门、独立审计和所有者新的明确决策；即使获准，也只能是 advisory routing，永久保持 `no_auto_verify + no_trading`。

`C-MDL-001 · C`：截至 2026-08-17 的仓库发布证据，v4 工件记为 `QUALIFIED_SHADOW`，而 V3 authentic-human blind-v2 尚未冻结。它不是对 AWS 此刻运行工件的现场证明；服务器答案仍须按 `FR-STATE-001` 重验。

## 9. 行情与防泄漏

- `FR-MKT-001 · P`：行情严格只读，不访问账户、余额、仓位、订单或执行信息。
- `FR-MKT-002 · P`：市场结果只能在事实结论之后作为事后审计上下文，不得反向证明消息真假、因果、严重度或模型标签。
- `FR-MKT-003 · P`：事后价格、收益、回撤、恢复和退市结局不得进入发现排序、模型输入、人工盲审或同期标签。
- `FR-MKT-004 · P`：T+5m/T+30m/T+1d 使用真实取得的窗口快照；错过即 `MISSED_WINDOW / UNAVAILABLE`，禁止以后来的最新价回填。
- `FR-MKT-005 · P`：界面必须显示 provider、asset、quote currency、采集时间/年龄和 fresh/stale/unavailable 原因。

## 10. UI、演示与前后端边界

### 10.1 总体体验

- `FR-UX-001 · P`：`Feed is the product`。用户先看到事件和证据；系统统计、模型和运维详情不得阻塞首屏。
- `FR-UX-002 · P`：设计必须有审美和人性化层级，而不是堆功能。专业感来自事实密度、证据、稳定工作流和克制视觉。
- `FR-UX-003 · P`：默认使用同页 master-detail；切换事件保留列表位置、筛选和上下文。站内动作默认当前页，只有原始外部证据链接可明确新开页。
- `FR-UX-004 · P`：一级操作、导航和下一步行动提示以中文为主；英文仅保留行业术语和机器状态。
- `FR-UX-005 · P`：证据权威、相关性、新颖性、冲突、模型置信度、人工状态和行情影响必须分开；禁止万能总分。
- `FR-UX-006 · P`：不得使用假订单簿、假 Level 2、装饰地图、无来源走势、交易按钮、霓虹、渐变、毛玻璃或发光边框制造专业感；红绿不得暗示买卖。
- `FR-UX-007 · P`：加载、空态、缓存、过期、来源降级和不可用必须用用户能懂的中文说明“发生了什么、是否使用旧数据、下一步怎么办”，不得暴露异常栈。
- `FR-UX-008 · P`：必须分别显示“Worker 最近成功”“最新发现事件时间”“来源降级”“备份可验证性”“服务存活”，不能合成一个绿色状态或把旧事件误称为采集停滞。
- `FR-UX-009 · P`：桌面、窄屏、键盘、焦点、44px 触点、WCAG AA、非纯色状态和 reduced-motion 属于发布验收。
- `FR-UX-010 · P`：本机保存视图只保存筛选和排序，不保存正文/身份、不联网、数量受限；不因轻量个性化先建账户系统。
- `FR-UX-011 · P`：事件阅读必须形成“列表筛选 → 同页预览 → 最高权威原始来源 → 返回原筛选位置”的闭环；无账户产品可以在单次浏览会话内提示状态、版本和证据集合的变化，但不得把会话记忆冒充跨设备历史。

### 10.2 四角色合同

| 角色 | 可见与可做 | 明确禁止 |
|---|---|---|
| Public | 事件流、中文事实、状态/新鲜度、证据、原始来源、方法，以及只读的预生成 Replay 结果 | 内部 ID、JSON、trace、运行时、Replay 控制、服务控制、写操作 |
| Reviewer | 待复核队列、完整证据、修订、冲突、只读行情、带身份理由的判断 | 部署、备份、模型运行和服务诊断 |
| Operator | 来源、Worker、备份收据、模型卡、Agent、Replay 和运行诊断 | 提交人审/盲审结论 |
| Admin | Reviewer + Operator 的 break-glass 超集 | 无确认的日常全权操作、绕过审计 |

- `FR-ROLE-001 · P`：Public、Reviewer、Operator、Admin 不得重新合并为一个全能前端；UI 和 API 两端都必须执行能力门。
- `FR-ROLE-002 · P`：公网只暴露 Public，API/docs 和内部角色绝不直接公网暴露。systemd 形态的 API/内部 UI 绑定 host loopback；Compose 的 API 只存在于私有容器网络，内部 UI 端口仅绑定 host loopback。内部能力使用独立强令牌和按需隧道。
- `FR-ROLE-003 · P`：公共演示可以查看只读、预生成的 Replay 结果和方法边界；启动、重置、切换模拟时钟和维护 Replay 数据属于 Operator。只服务答辩的 trace、数据库、模型运行、备份和服务按钮放在后台或报告。
- `FR-ROLE-004 · P`：`claudeUI` 静态原型永久归档为设计参考，不得成为第二套公共生产 UI。
- `FR-DEMO-001 · P`：LIVE、RECENT_CAPTURE、REPLAY、DEMO SNAPSHOT、SHADOW、FAIL 必须醒目标注；演示数据不得冒充实时。
- `FR-DEMO-002 · P`：Replay 使用模拟时钟，只呈现当时已经存在的证据，禁止未来信息泄漏；演示的最终动作是人工判断，不是交易。

- `FR-NOTIFY-001 · P`：Web-first；Telegram 是可选提醒和深链，默认 dry-run/off。

## 12. AWS、成本与资源约束

- `FR-COST-001 · P`：允许一台受资源约束的 AWS 主机及必要存储，不是无限支出授权。
- `FR-COST-002 · P`：先优化、停用无用服务，再扩容；积分、赠金或试用期不是增加实例、GPU、数据库、EIP、快照或常驻 LLM 的理由。
- `FR-COST-003 · P`：新增长期计费资源前必须说明目标用户价值、理论月费组成、失败/停止方式、数据保全和回滚。
- `FR-COST-004 · P`：月费按 compute、EBS、IPv4、流量、快照、突发 CPU 等现场估算；历史价格不能变成永久预算。
- `FR-COST-005 · P`：新加坡服务器和旧 Cloudflare 路由不是已批准的当前拓扑；未经新授权不得重建。最近一次“已退役/无残余资源”的判断属于带日期的 `C`，回答当前状态仍须重验。退役时逐项检查 EC2、EBS、EIP、snapshot、DNS 和边缘配置，停止实例不等于零成本。
- `FR-RES-001 · P`：受限主机必须保留 systemd/cgroup 总预算和 API/Web/Worker/Backup 分项上限；不得通过取消上限掩盖 OOM。
- `FR-RES-002 · P`：先限制并发、批量、缓存、日志和备份峰值，使用 swap/cgroup/重启隔离；只有测量证明仍不足才提出扩容。
- `FR-RES-003 · P`：磁盘 70% 开始评估，80% 暂停新增大对象；禁止删除事件账本、原始证据或唯一恢复点腾空间。
- `FR-RES-004 · P`：本地小模型只允许回环、限资源且默认 disabled。安装不会激活；只有资源冲突检查通过并获得独立运行授权后，操作者才可显式执行 `--activate` 持久启用，且不得与 Worker/Backup 同时运行。

## 13. 连续运行、备份、恢复与本地存储

- `FR-OPS-001 · P`：生产主形态是 AWS systemd + Nginx。当前 Compose/Caddy 只用于可移植开发/验证；在补齐等价的 memory/pids 上限、内部 UI 互斥、边缘 404 和发布验收前，不得在受限主机上晋级为生产，也不得形成并行生产真相。
- `FR-OPS-002 · P`：Worker 默认每 300 秒一轮；单一来源失败只使该来源/本轮降级，不阻断其他来源和后续周期。
- `FR-OPS-003 · P`：事件、原始观察、事件版本、证据和真实行情窗口不设 TTL；备份保留策略不作用于业务证据。
- `FR-BAK-001 · P`：在线备份每天一次，只保留最近一份完整恢复验证通过的日备份，周备份为零。
- `FR-BAK-002 · P`：新备份必须完成账本、运维库、证据/报告清单、哈希和隔离恢复验证后，才能删除上一份；失败必须保留旧恢复点。
- `FR-BAK-003 · P`：备份收据至少包含 snapshot ID、manifest hash、文件字节数/SHA-256、SQLite quick/integrity check 和验证时间。
- `FR-BAK-004 · P`：不得粗暴删除备份锁；只有租约到期且 owner 进程死亡后，在内核互斥保护内原子隔离。
- `FR-BAK-005 · P`：Public/API 不得因“检查备份”获得 root 目录读取权。无法探测时报告 `UNVERIFIABLE_PROTECTED/degraded`，不能冒充 fresh 或 failed。
- `FR-BAK-006 · P`：Git 恢复源码历史；生产恢复包必须进入操作者控制的私有存储或单独私有仓库，恢复口令与密文分离。公开 GitHub Release 只能放确认可公开的源码部署包、演示和模型/证据工件；不得把“公开仓库里的加密资产”描述成 private Release。
- `FR-LOCAL-001 · P`：Windows 本地工作站的大型迁移、发布、模型、备份和恢复工件默认使用 D 盘，避免继续占用紧张的 C 盘；Linux/AWS 路径仍由服务器部署合同决定。
- `FR-LOCAL-002 · P`：C→D 迁移分别记录 `copied / validated / cutover / source cleanup`；无哈希/完整性验证不得删除 C 盘原件。
- `FR-LOCAL-003 · P`：Windows 异机任务若重新启用，必须隐藏终端、加密、可验证、保留策略明确；不得恢复曾造成频繁弹窗的交互式短周期任务。

## 14. 安全与合规红线

- `FR-SEC-001 · P`：永久 `NO TRADING`：不得新增订单、撤单、仓位、余额、账户管理、券商写入、执行路由或仓位建议。
- `FR-SEC-002 · P`：禁止读取其他量化项目的策略、账户、凭据和业务数据，也禁止修改、启停或借用其他项目和 VPN。只有用户明确授权连接诊断时，才允许最小范围、保护现有连接的只读网络检查。
- `FR-SEC-003 · P`：密钥、令牌、SSH/TLS 私钥、Cookie、恢复口令、明文数据库和明文服务器快照永不进入 Git、报告、日志或 Public UI。
- `FR-SEC-004 · P`：Public 运行身份只能读取公共代码和最小环境，不能读取私有 env、数据库、报告和备份。
- `FR-SEC-005 · P`：内部令牌缺失、证据过期、角色不符或收据不一致时 fail closed；令牌使用 constant-time 比较。
- `FR-SEC-006 · P`：不能伪造学生作者身份、真实人工标签、教师批准、测试、提交、运行状态或现场验收。

`C-SEC-001 · C`：2026-08-17 现场查询显示本仓库是 `PUBLIC`，历史 Release 中仍有一份加密迁移资产。该事实不代表密文已泄密，但“private Release”假设已失效；本次细则变更不擅自删除历史恢复资产，后续保留/迁移/删除需单独决定。

## 15. GitHub、发布与现场真相

- `FR-REL-001 · P`：GitHub 是规范源码历史；`main` 是 reviewed baseline。每个短主题分支只承载一个聚焦变化；Codex 默认使用 `codex/<topic>`，人工或其他工具可以使用其他清晰短分支名，经 PR 和精确 HEAD 检查后合并。
- `FR-REL-002 · P`：每次提交前检查精确 staged diff、`diff --check`、status 和相关/完整测试；禁止未经检查的批量 `git add`。
- `FR-REL-003 · P`：Git 保存可维护源码、测试、合同和小型代表证据；确认可公开的完整 QA 批次、部署包和模型工件可以放公开 Release。生产恢复包不得放本公共仓库或其 Release，明文生产数据永不进入 GitHub。
- `FR-REL-004 · P`：正式发布绑定 release ID、commit、源清单、关键文件哈希、归档哈希和 sidecar；不能手改生成归档。
- `FR-REL-005 · P`：生产切换先做 manifest/path/link/device/敏感名/解压炸弹预检，再生成并验证恢复点；记录旧 symlink、操作者和 UTC 窗口，失败回滚并保留失败 release 供诊断。
- `FR-REL-006 · P`：新 tag/Release 只有在新归档、哈希、隔离恢复、生产切换和现场收据全部完成后才代表生产发布；本地测试或绿色 CI 不等于部署。
- `FR-REL-007 · P`：不 force-push 或重写已有历史；重复/大批材料通过控制未来新增治理。
- `FR-STATE-001 · P`：回答“服务器现在怎样”前，必须重新核验云资源、systemd、端点、Worker、备份和容量；若未核验，明确说是历史快照。

## 16. KPI 与下一阶段优先级

产品 KPI、工程健康、研究质量和课程证明分开报告；每个指标附测量窗口、样本量、数据来源和 `UNAVAILABLE`。

- `FR-KPI-001 · P`：发现指标包括 P0/P1 捕获延迟 P50/P95、来源成功率和新鲜度。
- `FR-KPI-002 · P`：证据指标包括可引用原文覆盖率、证据闭合率、冲突/不足率和更正响应时间。
- `FR-KPI-003 · P`：用户效率包括发现到打开原文的点击/时间、待复核队列年龄、保存视图使用和返回上下文保持。
- `FR-KPI-004 · P`：质量使用人工抽样准确率和撤回/更正证据；不得用模型自评或测试总数代替。
- `FR-KPI-005 · P`：信任红线是过期数据冒充实时、自动事实晋级、权限越界和交易接口，目标均为零。

当前开发顺序应当是：

1. 加快个人研究者看到首批事件和打开证据的路径；
2. 继续按事件家族完成有用的轻量细核和真实双盲标签，而不是继续堆模型；
3. 明确新鲜度、降级、证据不足和下一步行动；
4. 保持角色隔离、备份恢复、资源上限和发布可审计；
5. 测量用户价值后再决定是否增加来源、模型或基础设施。

## 17. 交付完成度

- `FR-DONE-001 · P`：进入已授权的实施阶段后，已核验且在范围内的问题必须修完并验证，或逐项写明延期理由、风险和后续门；不得把已知缺陷藏在“整体完成”中。
- `FR-DONE-002 · P`：所谓“完成”至少区分 `implemented / tested / published / deployed / live-verified`；任一层未发生就必须明确说未发生。
- `FR-DONE-003 · P`：面向用户的功能需同时检查正常、加载、空、错误、过期和降级状态，以及窄屏、键盘、可访问性和角色边界；只有 happy path 的页面仍是半成品。
- `FR-DONE-004 · P`：审计报告必须区分发现、建议、已实现、已验证、已部署和当前运行，不得把审计建议写成已经修复。
- `FR-DONE-005 · P`：重要阶段应分别从用户、领域/研究专家和开发/运维者视角复审；三者结论冲突时按用户优先级、安全边界和可验证证据裁决。
- `FR-DONE-006 · P`：完成范围内工作不等于扩张任务范围；需要新费用、外部协调或高影响动作时仍回到动作级授权门。

## 18. 产品变更门

每个新需求或规则修改必须记录：

1. 目标用户与实际任务；
2. 要改变的稳定规则和理由；
3. 成功指标及测量窗口；
4. 数据、证据、权限、隐私和泄漏影响；
5. 月度成本及停止方式；
6. 失败、回滚和数据保全方式；
7. 是否需要所有者新的动作级授权。

以下需求默认不得进入 Public 或正式判断链：

- 只服务答辩或内部证明；
- 主要展示数据库、模型、trace 或服务细节；
- 没有可测用户结果；
- 弱化只读、证据、不确定性或角色边界；
- 重复已有功能却增加导航和认知负担；
- 以云积分、技术新颖性或“更像大系统”为主要理由；
- 把 shadow、Replay、缓存或历史快照描述为当前正式能力。

## 20. 给以后人员和 Agent 的执行口令

开始任何非平凡工作前，必须先回答并在计划中体现：

1. 这是产品研究、模型、UI、运维、发布还是交易相关工作？
2. 它服务哪个优先级用户，是否缩短原始证据路径？
3. 是否保持“全极性事实层 + 下行风险路由特化 + 人工最终判断”？
4. 是否会把严重度、证据状态、模型标签和价格方向混为一谈？
5. 是否会使用未来行情、旧标签、来源捷径或后验结局？
6. 是否需要外发、云资源、DNS、密钥、生产或交易的单独授权？
7. 当前事实是否现场重验，还是只来自历史文档？
8. 失败后能否回滚，数据和唯一恢复点是否仍安全？

若任何答案不清楚，先停在只读检查或 shadow，不得用自信文案填补证据空白。
